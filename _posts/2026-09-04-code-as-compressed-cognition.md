チーム開発をしていると、不思議な現象に出くわす。

仕様書や議事録が残っていないわけではない。なにより、実装されたソースコードがリポジトリでチームに共有されている。誰でも手元のエディタで開いて、構文を一行ずつ追うことができる。

それなのに、そのコードを書いた本人以外のメンバーから見ると、まるで中身の窺い知れないブラックボックスのように見えてしまう。

一般的な知識管理（ナレッジマネジメント）の整理において、ソースコードは文字や記号として外部化された成果物であり、間違いなく「形式知」の一種である。言葉や図になっていない個人の頭の中のノウハウ（暗黙知）とは異なり、リポジトリに置かれたコードは誰でも参照できる。

しかし現場で起きているのは、「文字になっているのに、意図が伝わらない」という断絶である。

コードが明示しているのは、主に「コンピュータがどう動くか（実装された振る舞い）」である。その背後にある「なぜその設計にしたのか」「どんな選択肢を捨てたのか」「どの前提が崩れると壊れるのか」という設計判断やビジネスルールの文脈は、コードという形式知の中に必ずしも自動的には残らない。

なぜ、形式化されたはずのコードから文脈が消えてしまうのか。

この問題を解く手がかりが、エンジニアが情報をどう処理しているかという「認知戦略」の中にある。

## エンジニアの認知戦略：分割・圧縮・記録（保持／外化）

ソフトウェアエンジニアのTakami Torao（@torao）氏は、記事「[ソフトウェアの「設計原則」を、なぜ一部のエンジニアは生理的に嫌うのか](https://zenn.dev/torao/articles/20260502-differences-in-engrs-cognitive-strategies)」の中で、エンジニアが膨大な情報や知識を処理するプロセスを次のように整理している。

1. **分割（チャンク化）**：扱える大きさに分ける
2. **圧縮**：抽象化、ノイズ除去、パターン化によって自分が処理しやすい形に変換する
3. **記録**：
   - **保持**：脳のワーキングメモリに格納する（高速だが容量に限りがある）
   - **外化**：文章、図、コメント、既存コードなど自分の外側に配置する（容量はほぼ無限だが取り出しに一手間かかる）

同氏はこのモデルをもとに、情報を自分の脳内に留めて素早く動かす「圧縮型（Internalizer）」と、外部の図や構造に文脈を展開する「展開型（Externalizer）」という二つの認知傾向を提示した。

ここで注意したいのは、これが著者の長年の観察から組み立てられた説明モデルであり、実証済みの認知科学理論ではない点である。また、圧縮型と展開型は固定的な二分類ではなく、状況や場面によって使い分けるスペクトラム（傾向）として提示されている。

この説明モデルは、設計原則やドキュメントに対する態度の違いを鮮やかに照らし出す。そして同時に、「なぜ公開されたコードが他者にとってブラックボックスになるのか」という疑問に対しても、重要な示唆を与えてくれる。

## 「読めばわかる」の正体——設計判断の非可逆な投影

コードを書くとき、作者の頭の中では凄まじい密度の思考が行われている。

- なぜこのアルゴリズムやデータ構造を選んだのか
- この条件分岐の背景にあるビジネスルールや業務規程は何か
- 過去にどんなボツ案を試し、なぜそれを捨てたのか
- どんな前提や制約が崩れるとシステムが破綻するのか

「圧縮型」の傾向が強いエンジニアは、これらの前提や文脈を脳内で高度に圧縮し、最終的に「文法に適合した実行可能なコード」として外化する。

ここですれ違いが生まれる。

作者本人にとっては、画面上のコードは**脳内にある巨大な文脈と直結している**。たとえば次のようなコードを見たとき、作者の脳内では瞬時に理由が展開される。

```go
// 特別割引の適用判定
if user.MembershipRank == RankGold && order.TotalAmount >= 50000 && !user.HasFraudulentUseHistory {
    applySpecialDiscount(order)
}
```

作者の頭の中には、「ゴールド会員の優待ポリシー」「会計規程で決まった特別割引の基準額」「過去の不正利用対策のコンプライアンス要件」という業務文脈がすでに存在している。だから作者は「コードを見ればわかるでしょ」と自然に感じる。

しかし、そのコードをレビューする同僚や、後から改修を引き継ぐメンバーの脳内には、作者と同じ文脈が存在しない。

コードは、無数の試行錯誤やトレードオフを含む**設計判断全体の「非可逆な投影」**である。実装された処理はコードから追えても、そこから「なぜその値や構造が選ばれたのか」という採用理由を一意に復元することはできない。

他者にとっては、文脈を復元するための手がかり（補助線）がなければ、画面のコードは「なぜ動いているのか分からない、触るのが怖い文字列」に見えてしまう。

## 振る舞いの外化と、判断理由の外化は同じではない

コードを書くことは、間違いなく知識の外化（形式知化）の一種である。

しかし、コンピュータに向けて「実行可能な振る舞い（How）」を外化することと、チームに向けて「設計の判断理由や制約（Why）」を外化することは、同じではない。

| 観点 | コード（振る舞いの外化） | 足場（判断理由の外化） |
|---|---|---|
| **主な対象** | コンパイラ・実行環境・読み手 | チームメンバー・未来の開発者・AI |
| **表現されるもの** | 実行手続き、型の定義、制御フロー、インターフェース | ドメインの概念、不変条件、ビジネスルールの根拠、決定理由 |
| **コード単体では残りにくいもの** | 捨てた選択肢、回避した罠、業務上の動機、変更時の前提 | 一行ごとの細部実装 |

コードに残るのは、検討された複数の設計案のうち、最終的に採用された実装である。背後にあったボツ案や、業務上の複雑なルールや制約は、実装の行間にはそのまま残らない。

もちろん、適切な命名や型、アサーションを使うことで、コード自身に設計意図をある程度埋め込むことはできる。しかし、それだけでは「なぜその閾値なのか」「どの規程に基づいているのか」という文脈までは支えきれない。

「コードという形式知があること」と、「チームがその設計判断を理解し、修正できること」の間には、依然として大きな距離が存在する。

## AI駆動開発と「説明主体のないコード」

この問題は、AIによるコード生成が普及したことで、より顕著になっている。

人間の開発者であれば、どれほど文脈が省略されたコードであっても、書いた本人に「ここはどういう意図で書いたのか」を直接尋ねることで、記憶から判断理由を再構成できる余地があった（もちろん、本人が忘れてしまうリスクはある）。

しかし、AIが短時間で大量のコードを出力できる現代では、状況が変わる。

AI生成そのものが直ちにブラックボックスを生むわけではない。仕様やテスト、設計方針を与えて生成させ、人間が理解・検証した上で取り込むなら問題は少ない。

問題なのは、**コードの生成速度が人間の検証・理解・記録の速度を上回り、誰も設計判断を引き受けないままリポジトリへマージされること**である。

プロンプトを投げた開発者自身すら、「なぜこの構造になったのか」「どんな前提条件に依存しているのか」を説明できないとき、リポジトリには**「説明主体の存在しないコード」**が残される。本稿では、この状態を便宜的に「合成暗黙知」と呼ぶ。

テキスト化のコストが劇的に下がったからこそ、形式化された文字の裏にある「文脈」をどう残すかが問われている。

## チームに必要な「3層の足場」

では、コードが持つ文脈の断絶を埋めるために、すべての行に詳細な日本語解説を書くべきなのだろうか。

それでは膨大な保守コストがかかり、コードの変更にドキュメントが追従できず形骸化してしまう。同氏の記事が示すように、認知傾向の違いを無視して一律のドキュメント作成を強制しても現場は疲弊する。

必要なのは、全行の翻訳ではなく、**他者が設計判断やビジネスルールを安全に展開できるようにするための「足場（スキャフォールディング）」**を整えることである。この足場は、大きく3つの層に整理できる。

### 1. コード内の足場：ドメインモデルによる意図の埋め込み

ドメインモデルとは、値オブジェクトや集約といったパターンを単に集めたものではない。対象業務についてチームが理解した**概念、その関係、ルール、振る舞い**を表現したモデルである。ユビキタス言語はそのモデルを議論し表現するための共有言語であり、値オブジェクトや集約はモデルをコードに表すための構成要素となる。境界づけられたコンテキストは、そのモデルと言語が一貫した意味を持つ適用範囲を定める。この整理は、Eric Evansの「[Domain-Driven Design Reference](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf)」に基づいている。

* **ユビキタス言語（Ubiquitous Language）とドメインモデル**: ドメイン専門家と開発者が共有する言葉を、会話、文書、テスト、コードで一貫して使う。コード上の名前と業務概念を結びつけ、モデルを継続的に更新する。

* **値オブジェクト（Value Object）**: 単なる `int` や `string` ではなく、`MembershipRank` や `Money` のように業務上の意味を持つ値として表現する。その値自体に固有の制約や振る舞いは値オブジェクトに持たせる。

* **ビジネスルール（Policy／Specification）**: `if` 文に埋もれた業務判断に名前を与え、`SpecialDiscountPolicy` や `DiscountEligibilitySpecification` のような明示的なモデルとして表現する。ただし、すべてのルールを機械的に別クラスへ移すのではない。値に固有のルールは値オブジェクトに、一つの整合性境界で守るルールは集約に、複数の概念をまたぐ判断はポリシーや仕様、ドメインサービスに置く。

* **集約（Aggregate）と不変条件**: 絶対に崩してはならない整合性を守る単位として集約の境界を定め、その入り口となる集約ルートを明示する。外部からの変更を集約ルートに集約することで、他者が一度に考慮すべき整合性の範囲を限定する。

* **境界づけられたコンテキスト（Bounded Context）**: 同一のモデルと言語が一貫して適用される範囲を明示する。同じ「会員」や「注文」という言葉が別の文脈では異なる意味を持ち得ることを認め、モデル間の食い違いを見つけやすくする。

たとえば、元の条件式に含まれていた割引可否の判断に業務上の名前を与えると、コードからルールの所在をたどりやすくなる。

```go
// 割引可否という業務判断を、名前のあるポリシーとして表現する
if specialDiscountPolicy.IsEligible(user, order) {
    applySpecialDiscount(order)
}
```

ただし、この名前だけで「なぜ基準額が5万円なのか」まで説明できるわけではない。成立条件はテストに、規程の根拠や変更理由はADRなどに残すことで、別の層から文脈を補う。

### 2. 実行可能な仕様としての足場：テストコード

単なる入出力の確認にとどまらず、「ゴールド会員かつ一定金額以上で、不正利用履歴がなければ特別割引を適用する」といったビジネスルールの成立条件そのものをテストケースとして記述する。テスト名に業務規程のIDや要件を対応付けることで、テストがそのまま「動く仕様書」として機能する。

### 3. コード外の足場：ADR（Architecture Decision Record）

コードには「採用された案」しか残らない。だからこそ、「なぜ他の選択肢を捨ててこの設計を採用したのか」「どんなトレードオフを受け入れたのか」という決定プロセスを、短いADRとして記録に残す。

これら3層の足場は、過剰な解説ドキュメントではなく、**コードを読む他者が迷子にならずに設計意図を展開するための「補助線」**である。

## 答え責任を引き受ける

「コードがあるから十分」という前提は、チームに必要な共有水準とのずれを見えにくくする。

コードは思考と判断の結晶であり、優れた形式知である。しかし同時に、無数の判断を削ぎ落とした圧縮物でもある。文脈を持たない他者にとっては、どれほど綺麗なコードであっても、その意図を読み解くための足場が要る。

ここで言う「答え責任（Answerability）」とは、**問われたときにその設計やコードの理由を説明し、その結果を引き受ける責任**のことである。

AIがコードをいくらでも生成できる時代だからこそ、重要なのはコードの量を増やすことではない。
コードという形式知の外側に、チームがその意味を展開し、修正を引き受けられるだけの**「認知の足場」をどれだけ残せるか**である。
