# 原典理解とハルシネーション対策

## 原則

- 中心的な主張は原典で確認する。検索結果の抜粋、AI の記憶、第三者の要約だけで確定しない。
- 正確な表記と、主張の正確な理解を別々に検証する。著者名、題名、URL、日付が正しくても、要約が正しいとは限らない。
- 原典の記述、原典著者の仮説、筆者の推論、筆者の造語、実務上の提案を区別する。
- 引用符と Markdown の引用ブロックは原文を再現するときだけ使う。意訳や要約を引用のように見せない。
- 技術概念は、その標準、公式文書、原著、一次論文を優先する。解説記事は入口や補助資料として扱う。

## 証拠パック

原典に依存する記事ごとに次を置く。

```text
research/<slug>/
├── sources.yaml
├── claims.md
└── snapshots/       # 任意。原則として Git には入れない
```

`sources.yaml` の例:

```yaml
version: 1
article: _posts/YYYY-MM-DD-slug.md
sources:
  - id: author-year-short-name
    type: web-article
    title: "原題"
    author: "著者または組織"
    canonical_url: "https://example.com/original"
    published_at: "YYYY-MM-DD"
    updated_at: "YYYY-MM-DD"
    retrieved_at: "YYYY-MM-DD"
    local_snapshot: "snapshots/source.html"
    sha256: "..."
    license: "unknown"
```

不明な任意項目を推測で埋めない。省略するか `unknown` とし、必要なら notes に未確認理由を書く。`canonical_url` は検索結果や転載先ではなく原典を指す。

`claims.md` は次の列を使う。

```markdown
| ID | Draft claim | Source | Locator | Class | Status | Notes |
|---|---|---|---|---|---|---|
| C001 | 記事中の確認可能な主張 | source-id | 節名・ページ・段落 | source-fact | verified | 確認内容 |
```

Class:

- `source-fact`: 原典が事実・定義・結果として述べる内容
- `source-hypothesis`: 原典著者のモデル、解釈、仮説、提案
- `author-inference`: 原典から本記事の筆者が導いた推論
- `coined-term`: 本記事で導入する語や独自定義
- `recommendation`: 実務上の提案

Status:

- `verified`: 原典と位置を確認し、表現が一致する
- `qualified`: 条件や限定を加えれば維持できる
- `unsupported`: 現在の根拠では支えられない
- `pending`: 未確認

## 確認手順

1. 記事から、固有名詞、URL、日付、数値、引用、技術的定義、外部資料に帰属させた主張を抽出する。
2. **同定検証**として原典を開き、著者、アカウント名、題名、公開・更新日、正規 URL を照合する。到達できない情報を推測で補完しない。
3. **意味検証**として主張の前後、定義、但し書き、対象範囲、反例を読む。原典が事実として述べたのか、著者の仮説や提案なのかも確認する。用語だけの一致で同義と判断しない。
4. **利用検証**として、記事が原典の射程を広げていないか、原典の留保を落としていないか、相関を因果へ変えていないかを確認する。
5. 各主張を `claims.md` に分類し、節名、ページ、見出し、段落など再確認できる位置を記録する。中心的な主張では、Notes に重要な限定や反対方向の記述も残す。
6. 原典の射程より広い表現は狭める。維持できない主張は削除するか、筆者の仮説として明示する。
7. 記事の修正後、結論を疑う立場でもう一度 locator の前後を読み、主張表と本文を突き合わせる。公開直前にも変更され得るウェブ資料を再確認する。

## ローカル保存の判断

ローカル保存は再現性と差分確認に役立つが、保存物が最新・真正であることを保証しない。必ず取得日と正規 URL を残す。

- 記事の中心であり、改訂されやすい、またはページ位置が不安定な資料は snapshot を検討する。
- DOI、版、公開日が固定されている論文・標準は、まずメタデータと locator を残す。必要な場合だけ取得する。
- 著作権や利用条件が不明な全文は公開リポジトリへ commit しない。`snapshots/` に私的保存し、Git にはメタデータ、検証メモ、許容範囲の短い引用だけを残す。
- 自作資料や再配布可能な資料を commit する場合はライセンスを記録する。
- snapshot を登録する場合は SHA-256 を記録し、後から同一性を検査できるようにする。

## 自動検査の限界

`verify_sources.py` は YAML、主張表、参照 ID、locator、snapshot のハッシュを検査する。原典の意味を理解したことや、記事の主張が真であることは自動判定しない。最終判断では原典本文を読む。
