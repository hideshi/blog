# 執筆・編集・レビュー

## 記事の軸

AI 駆動開発とソフトウェア設計を、認知作業の外部化と答え責任から考える。ただし、結論を先に決めて記事をこの軸へ合わせない。素材から得た観察と、筆者が行う読み替えを分ける。

使いやすい構成は次の通り。すべての記事に強制しない。

1. 読者が経験している具体的な場面を置く。
2. 便利さの裏で、どの負担がどこへ移ったかを示す。
3. 概念間または工程間の対応関係を固定する。
4. 比喩や読み替えが通用する範囲と限界を書く。
5. 読者が判断できる条件で閉じる。

## 入口を明快にする

title、description、導入 2 段落、X 投稿文は本文なしでも意味が通るようにする。

- 主語と動作を先に置く。
- 本文の説明を必要とする比喩や造語を入口に置かない。
- 比喩は具体的な動作を書いた後で、一度だけ名付ける。
- 「誰が、何を、いつ、なぜするか」を読者が言い返せるか確認する。
- description は記事の片側だけを誇張せず、問いとずらしを 120 字前後で表す。

## 論理と用語

- 観察から一般論へ移る箇所では、対象範囲と推論であることを明示する。
- 比喩は説明の道具であって証拠ではない。異なる比喩を同じ意味のように連結しない。
- 技術用語は初出で、その記事に必要な粒度だけ定義する。
- 複数の概念を並べるときは、同列か、包含関係か、制約か、境界かを示す。上位概念と構成要素を同列の箇条書きにしない。
- 独自の意味で使う語は「本稿では〜と呼ぶ」と宣言し、既存の学術用語・業界用語に見せない。
- 構造上の問題を、個人の能力や態度だけの問題へ縮めない。

## 具体例

- 例のコード、説明、テストが同じ業務ルールを表しているか確認する。
- 条件式だけを示す場合も、変数の意味、境界値、例外、不変条件の所在を説明する。
- DDD の語を使う場合、ユビキタス言語はモデルを形成し表現する共有言語、値オブジェクトと集約はモデルを実装するパターン、不変条件は集約などが守る制約、境界づけられたコンテキストはモデルと言語が一貫する適用境界として区別する。
- ビジネスルールはこれらと同列の「部品」とは限らない。モデルの振る舞い、制約、ポリシーとして各所に表現される横断的な内容である。記事では、どのルールをどのモデル要素が担うかを書く。

## レビューの出力

重要度順に、次をセットで示す。

1. 問題のある記述と位置
2. なぜ問題か
3. 原典または概念との関係
4. 最小の修正文案

単なる好みと、事実誤認、論理の飛躍、読者が誤解する危険を区別する。問題が見つからない観点も、その旨を明記する。

## サイト内の接続

既存記事や `about.md` の研究論文へ接続するのは、論点上必要な場合だけにする。過去記事や特定の論文群を毎回の結論に強制しない。リンク先が実際に本文の主張を支えるかを読み直す。
